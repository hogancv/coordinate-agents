# 自动保存与恢复 Codex 原生对话

适用于 **`f9f0210` 及之后的源码实现**，核对日期为 2026-10-21。
此流程纳入 **Web 3.0.2**。最初源码阶段的包版本仍为 3.0.1，因此历史行为用提交阶段区分，不代表 npm 3.0.1 已包含这些能力。
旧设计与验收记录中的恢复后人工确认步骤属于历史流程，见文末的适用版本说明。

默认协作会保留 Task、Git 工作区、协作轮次和 Timeline。关闭任务会停止本任务拥有的
终端；“重新开启任务”恢复原 Codex 对话。“Restart Pair / 重启双终端”不是恢复入口。
已有原生绑定或预留恢复目标的任务会在关闭终端前拒绝创建新对话，以保护不可覆盖的原绑定；
继续原对话请重新开启，新上下文请新建任务。未绑定任务、自定义双终端保留原有重启流程，归档任务仍不可恢复。

## 动作表

| 动作与入口 | 条件和范围 | 对终端的影响 | 保留内容与后续行为 |
| --- | --- | --- | --- |
| 重连终端：刷新浏览器或重新连接 | 原 Session Host 仍在运行 | 浏览器重新连接原 Session，不启动原生 Resume | 保留现有终端及仍可用的输出；输出保存有界，不承诺完整历史回放 |
| 新建任务：New task / 新建任务 | 当前项目，默认协作或自定义双终端 | 创建新的任务终端；默认协作初始化双方角色 | 创建新 Task 和上下文，不恢复其他任务的原生对话 |
| 关闭任务：状态旁红色关机图标 | 当前选中任务；Web 二次确认后执行 | 停止本任务拥有的终端 | 保留 Task、Git 工作区、绑定或预留 UUID、轮次和 Timeline，不派发指令 |
| 关闭所有终端：品牌旁关机图标 | 仅当前项目；Web 二次确认后执行 | 逐个关闭该项目尚未关闭的任务终端 | 保留内容同“关闭任务”，不影响其他项目 |
| 重新开启任务：恢复图标／兜底框“继续对话” | 未归档默认任务处于 CLOSED、EXITED、DEGRADED 或 ERROR；原 UUID 合法且无锁存冲突 | 复用仍有效的终端；缺失 Codex 用 `codex resume <uuid>` 恢复，缺失执行端创建新 Session | 保留 Task、Git 变更、绑定或目标、轮次和 Timeline；正常初始化完成后直接就绪，不要求人工确认身份 |
| 恢复执行端：同一恢复图标按状态改名 | 默认任务的 Codex 仍存活且归属正确，Antigravity 已退出或缺失；UUID 校验同“重新开启” | 保留 Codex 的 Session 和运行代次，只补建执行端并初始化当前角色/helper | 不恢复 Antigravity 原对话，不重放旧指令；新执行端不能完成原执行端拥有的旧轮次 |
| 继续启动：Web 刷新自动调用 `workspaceTaskContinue` | 已有默认任务处于 STARTING 或 AWAITING_INPUT | 登录、信任处理后重新检查已有终端，继续初始化 | 不创建新对话；角色注入结果不确定时报告错误，不自动重发 |
| 重启双终端：`workspaceTaskRestart` Runtime/HTTP 接口，当前 Web 无独立按钮 | 未绑定且未预留 UUID 的默认任务，或自定义任务；归档任务拒绝 | 关闭旧终端后新建 Session；默认任务若已有绑定或目标，在关闭前即拒绝重启 | 保留 Task、工作区和历史；默认任务重置当前协作状态。它创建新上下文，不等同原生恢复 |
| 归档任务：任务右键菜单 | 未归档任务 | 关闭拥有的终端并隐藏任务 | 记录保留到显式清理归档数据；归档任务不能重新开启 |

恢复状态 `READY` 要求两个终端都存活、Task/Slot/Session/运行代次归属一致、双方启动槽位均为
`READY`，且 Codex 没有锁存身份冲突。Codex 缺失或身份冲突为 `FAILED`；执行端缺失或启动未完成
为 `PARTIAL`；待启动阶段可以保持 `STARTING`；关闭或归档显示 `CLOSED`。
历史数据中的 `AWAITING_CONFIRMATION` 继续可读，按当前事实派生显示，不再是必需操作或就绪前置条件。
任务生命周期和恢复就绪均不证明实现工作已经完成。

UUID 兜底框只用于提供恢复目标，不是恢复后的身份确认关卡。关闭操作的二次确认、CLI 登录和信任提示、
Custom Prompt 就绪确认、审查反馈发送确认，仍是各自独立的流程。
本表描述 Web Workspace Task，不等同于[结构化工作流](../structured-workflow.md)中的 Legacy `task resume` 命令。

## 正常流程

1. 新建默认协作任务。支持的本地 Codex CLI 0.163.x 会在原生启动事件和记录可用后，
   自动将界面从“正在识别对话”更新为“对话已保存”。保存绑定无需运行 `/status` 或输入 UUID。
2. 关闭任务。原生对话绑定、轮次、Timeline 和恢复元数据保留。
3. 点击状态旁的“重新开启任务”。有合法历史绑定时直接取出原 UUID，调用原有原生 Resume，
   不展示完整 UUID 表单，也不重新发送 Codex 角色 Prompt 或中断前指令。
4. 终端恢复并完成正常登录、信任和角色初始化后，任务直接就绪，无需再次核对 UUID 或人工确认。
   新的协作派发和审查使用当前 Session 和 Runtime Generation 校验。旧版保存的“待确认”任务
   同样按当前终端状态直接显示就绪。

已有 Antigravity Session 合法且健康时复用；否则按用户配置、wrapper / agy-proxy
重建。执行端恢复失败会保留有效 Codex，重新开启仅补缺失的执行端。原执行端的轮次不能
由新执行端提交回执。对中断指令、不确定投递均不自动重发。

## 何时需要人工处理

未成功绑定、CLI 版本不支持、远端运行时、记录缺失、项目或 UUID 占用冲突、原生来源未知、
采集失败或恢复失败时显示兜底入口。有历史 UUID 时自动预填。异常退出和部分恢复的任务
同样有恢复入口。项目或任务切换会关闭对话框；仅打开或关闭对话框不会启动恢复。

“已发现候选”“已可靠绑定”和“当前 TUI 身份已验证”是不同事实。JSONL 存在、进程存活、
历史绑定都不能证明当前 TUI；任务就绪不依赖人工确认。执行 `/new` 等切换后，收到不同的可信原生
启动事件并核对主 CLI 记录时，会保留原绑定、锁存身份冲突，并阻止新派发与审查。
日志是异步的，不能保证立即或完整检测切换；切换后不要继续协作。冲突不能通过填写新 UUID 清除，
需要检查原始任务绑定。Ready 标签不代表持续实时验证。

## 本地配置与隐私

采集使用官方 OTLP/HTTP JSON 日志：Detached Session Host 为每次启动创建仅在内存中保存的
随机本地接收地址，使用 `--no-daemon` 隔离进程，并通过本次启动参数覆盖 OTEL 日志导出端。
Prompt 和响应日志关闭；已有 Trace/Metric 导出、通知、模型、权限、认证和登录行为保留。
Hooks 仍禁用，不绕过信任审查，不修改全局 Codex 配置。

只用事件给出的精确 UUID 查找有效 `CODEX_HOME` 或默认目录中的主 CLI 原生记录，验证
canonical cwd、版本及来源。不会按最新文件或时间猜测，也不会无限轮询或无界扫描。
现有 Identity Store 负责 Session / Generation / Revision CAS、跨任务占用、不可静默覆盖
和原子持久化。采集失败不影响原有手动恢复。

原生行为、平台范围及独立验收命令见[开发与验证说明](../codex-native-auto-binding.md)。
