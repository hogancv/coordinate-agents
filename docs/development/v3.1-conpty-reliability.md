# V3.1 Windows ConPTY 与终端可靠性开发记录

日期：2026-10-11。稳定基线：`origin/main` 的 `0b924f8`（V3.0.0 Web-first）。开发分支：`codex/v3.1-conpty-reliability`。本次不发布版本，npm 版本仍为 `3.0.0`，node-pty 仍为 `1.1.0`，没有生产依赖或 lockfile 变更。

## 结论与验收边界

当前保持 Windows Node 22/24 的 **auto → stdio-fallback** 策略。新增 **进程级、严格 native 实验**，失败不降级。macOS arm64 Node 22.23.3 / 24.17.0 已通过真实 Native PTY 集成测试。授权手动 CI 已验证 Windows 22/24 的产品 Native Host 交互与生命周期；原始库自然退出的 worker 清理仍失败，因此不改变默认策略。Ubuntu Native 已通过。最终 Runner 明细见验收补录。

原来的 Windows 限制并不能证明 Node 22 的 ABI 不兼容。已读取的历史 CI 日志证明 Session/目录清理失败；没有足够的原生崩溃栈定位到 ConPTY 或 Node 的单一根因。本次不会把修复普通 Session 生命周期问题描述成已修复 Windows 原生崩溃。

## 历史证据与故障分类

限制最早出现在 `500c752` / [PR #17](https://github.com/hogancv/coordinate-agents/pull/17)，最后一个子提交说明为 `fix: stabilize Windows Node 22 session cleanup`。

通过 `gh` 获取了以下日志：

- [32867508239](https://github.com/hogancv/coordinate-agents/actions/runs/32867508239)，`2e0f39a3`，尚未限制 Windows native：external Adapter 注册 fixture 最后 `rmSync` 出现 `EBUSY`。
- [32868040172](https://github.com/hogancv/coordinate-agents/actions/runs/32868040172)，`3aa8b166`，尚未限制 Windows native：同样的目录 `EBUSY`，另有 MCP persistent Session 布尔断言失败。普通 Session open/write/read/close 测试在同一 Windows Node 22 作业中通过。
- `4cb639cd` 随后引入 Windows Node 22+ fallback；历史成功不等于真实 ConPTY 验收。

| 分类 | 已有证据 / 目前处理 |
| --- | --- |
| 加载失败 | Windows 的 `require('node-pty')` 仅加载 JS 入口，`conpty.node` 在 `WindowsPtyAgent` 构造时才加载。独立探针显式检查绑定；缺少依赖的独立 checkout 测试证明 auto 可诊断 fallback、native 必须失败。历史日志未证明 ABI 加载失败。 |
| 初始化失败 | 公开的 `spawn` 同时完成 pseudo console 和进程创建，不能仅凭调用失败精确划分。已按 node-pty 的已知错误模板分类；原始探针把调用前阶段与绑定阶段分开。严格 Windows 实验拒绝不支持 ConPTY 的旧 build，防止 WinPTY 冒充 ConPTY。 |
| 启动失败 | 旧 Manager 超过 5 秒后仍返回 `starting`。未绑定 endpoint 的 Host fixture 已复现，并修复为明确失败与进程回收。稳定性窗口仍保留。 |
| 运行时错误 | 已注入真实 PTY 对象的 EPIPE 事件，验证错误监听、脱敏固定原因及退出；这是故障注入，不是 Windows 自然崩溃复现。正常 native keyboard / ANSI / UTF-8 / resize 使用真实 PTY。 |
| 关闭清理失败 | 历史 Windows EBUSY 已确认。新测试同时检查 CLI、后代、Host 存活和目录删除；macOS 已通过。忽略 SIGTERM 的未就绪 Host 在本机复现泄漏，现加入有界 SIGKILL 升级。Windows 句柄释放仍需真实 Runner 验收。 |
| 测试/启动误判 | 同一历史作业已有 native Session 测试通过，但后续 fixture 清理失败；清理异常可能覆盖实际断言。V3.0 的 Windows 独立 executable 文件、stdio close/drain、IPC init 消费顺序修复全部保留。新 raw probe 比较 attached 与 detached，避免仅测库 import 或 HTTP 200。 |

node-pty 1.1.0 的源码使用 N-API，并且 Windows exit callback 有 `Napi::Error::Fatal` / assert 路径。源码存在这些路径不能证明本次历史失败经过它们。没有证据要求升级 node-pty，因此暂不升级。

## 实现范围

| 文件 | 改动 |
| --- | --- |
| `pty-runtime.mjs` | 严格实验模式、固定的脱敏 failure stage/code、平台/Node 信息；native stream 错误处理；stdio UTF-8 decoder；UTF-8 安全尾部截断；截断事实；清理定时器；Windows tree kill 顺序。 |
| `session-host.mjs` | 将 backend、diagnostics、cols/rows 持久化；close 返回 active 时不提前关闭 endpoint，允许 Manager 升级清理。 |
| `session-manager.mjs` | 公共记录与 durable 记录保留诊断/尺寸；捕获 owned fork 的异常退出；启动超时明确失败并回收；未就绪 Host 的有界强制退出。旧 terminal 记录的 PID 不用于强制杀进程，避免 PID 复用伤及其他进程。 |
| `workspace-task-runtime.mjs` | 双终端的既有 Session view 添加 backend、diagnostics、cols/rows。任务/角色/协议保持不变。 |
| `session-service.mjs` | 无需修改；既有 forwarding 自动带出新增 Session 字段。 |
| `app.js` / `terminal-model.mjs` | 现有 footer 显示 Native PTY / stdio fallback / unknown；tooltip 提供脱敏诊断。Resize 仅在后端确认后记为同步，允许失败后相同尺寸重试，并修复 pending A→B→A。 |
| `.github/workflows/web-ci.yml` | 增加仅手动的 `native_pty_regression`，不扩大日常矩阵；保留 `windows_regression`。 |

诊断不复制 argv、env、Cookie、Token、登录凭据或会话内容。新增的失败原因均为固定代码。已有会话输出仍沿用既有脱敏和有界读取；没有新日志收集系统。

API 只添加字段，不改变现有操作或 schemaVersion。旧记录缺少这些字段时返回 null，UI 显示 unknown，不能据此声称 native。`nativeStatus` 区分 pending/running/unavailable/disabled/exited/failed，failure 包括 selection/load/initialization/spawn/runtime/exit/host/cleanup 阶段。

## 最小复现与运行方法

先在独立开发 checkout 执行 `npm ci`。探针只启动仓库内离线 Node fixture，不调用 Codex、Antigravity 或模型服务，不读取登录凭据。

```sh
# 原始 node-pty：显式绑定加载、TTY、输入、中文/ANSI、尺寸、自然退出和目录释放
node scripts/diagnose-native-pty.mjs
node scripts/diagnose-native-pty.mjs --attached

# 正常日常回归：真实 fallback、缺少绑定、错误注入、UTF-8、前端尺寸队列
npm run test:pty

# 必须是 native，绝不把 fallback 的通过记成 native 通过
npm run test:pty:native
```

`diagnose-native-pty.mjs` 在独立 worker 中调用原始 node-pty，阶段通过 IPC 回传，忽略普通 stdio 时仍可观察进度。20 秒监督超时、worker exit code/signal、最后阶段、CLI 存活和临时目录删除都进入 JSON。成功需要 worker **自然退出**，不能用 `process.exit(0)` 隐藏 native worker/handle 泄漏。绑定、TTY、尺寸和子进程事实都来自实际库或实际子进程，不来自产品 backend 字符串。

`scripts/pty-probes/terminal-probe.cjs` 在 raw mode 接收 Enter、Backspace、四个方向键、Ctrl+C，并计算大粘贴内容 SHA-256；使用 alternate screen、clear/home/color 重绘。子进程查询真实 console window size；Windows 不一定发送 Node resize event，因此还轮询 `getWindowSize()`。正常 `/exit` 和异常 `/crash` 分别退出 0 / 9；`/spawn` 创建后代，验证进程树释放。

实验开关：

```sh
# POSIX：仅本次启动进程及其 owned Host 使用
COORDINATE_AGENTS_PTY_MODE=native node bin/coordinate-agents.mjs web --root <offline-test-root>
```

```powershell
# PowerShell：当前进程环境；结束测试后清除
$env:COORDINATE_AGENTS_PTY_MODE = 'native'
node bin/coordinate-agents.mjs web --root <offline-test-root>
Remove-Item Env:COORDINATE_AGENTS_PTY_MODE
```

支持 `auto`（默认、保持平台政策）、`native`（Node >=20、严格无 fallback）、`stdio`（显式兼容后端）；拼写错误直接拒绝。不要写入用户 config，不设置系统环境变量。已发布的 V3.0.0 不含此开关；本开发分支不做任何发布操作。实验应使用独立 root，因为已有 Session 持久化与复用契约不会自动重启一个历史 fallback Session。

浏览器离线 QA 入口：`node scripts/pty-probes/native-browser-server.mjs`。它输出临时 URL/directory，建立独立用户配置、真实 executable 和双终端 fixture；SIGTERM/SIGINT 会关闭 owned Sessions 并删除临时目录。此入口仅供人工/ego-browser QA，不进入 npm 白名单或日常自动测试发现。

## Runner 验收补录

第一轮 [38138450785](https://github.com/hogancv/coordinate-agents/actions/runs/38138450785)，提交 `aaaf21d`；第二轮 [38139026280](https://github.com/hogancv/coordinate-agents/actions/runs/38139026280)，提交 `726630a`。两轮 overall 均为 failure，未把失败平台当作通过。

Windows Node 22.23.3 / 24.21.0，build 10.0.26100、x64：原始探针真实 `conpty.node` 加载、TTY、输入、中文、ANSI、resize 和 CLI 0 退出全部到达 complete，但独立 worker 20 秒后仍活着，`timedOut:true`、`childAlive:false`、`failureStage:cleanup`。同一作业的产品 Native Session Host open/write/read/resize、重连、正常/异常退出、Host SIGKILL、后代关闭和目录删除通过。因此不能把问题归为“绑定加载失败”或“Node 22 无法创建 ConPTY”。Node 20.20.2 的 raw probe 出现同样资源清理故障，进一步排除了它仅特有于 Node 22/24 的假设。

node-pty 1.1.0 源码中的实际路径：`WindowsPtyAgent._$onProcessExit()` → `_flushDataAndCleanUp()` → `_cleanUpProcess()` 只销毁 outSocket；`ConoutConnection` 的 worker 在 `conoutSocketWorker.js` 中创建并监听一个 server，自然退出路径没有调用 worker dispose。这解释了“CLI 退出、TTY 交互正常、独立库进程仍留存”的复现。它是目前有源码和运行证据的资源释放障碍；它不能证明历史 PR #17 的每一个 EBUSY 或断言错误都来自同一原因。

第二轮的 `pty.kill()` after onExit 对比能令 raw worker 自然退出。然而 `WindowsPtyAgent.kill()` 会异步启动 console-list helper，再向返回的 PIDs 发信号；helper 超时 5 秒后退回原 PID，且没有已退出/身份校验。已退出 PID 可能被重用，因此该方法不能作为安全 disposal。实验选项和 CI 对比步骤已移除，不进入生产修复。当前 stable registry 的 node-pty 仍为 1.1.0，没有经证明可替代的稳定升级。

生产路径保留独立 Host：在 drained terminal fact 持久化之后退出 Host，释放其 ConPTY worker/文件句柄。Windows force-close 和 stream-failure 使用当前 owned process tree；不在 taskkill 完成后再调用会延迟按旧 PID 发信号的 node-pty kill。另有固定码 `uncaughtExceptionMonitor`，保留 Node 默认崩溃行为，不吞掉异常、不写原始栈或私密错误值。

Ubuntu Node 24 第一轮因为新增的 error observer 与 node-pty 对 POSIX 正常 EIO/errno 5 的处理不一致而失败。修正为同样的正常读端结束分类后，第二轮完整 Native suite、原有 Session 回归与 raw 两种启动方式都通过；没有通过跳过断言处理。Windows 18 fallback 和 macOS 22 Native 两轮均通过。Windows 20 的第二、三轮原有 Session 回归通过，但专门的 unready fixture 提前退出。仅限制 Unix SIGTERM hook 没有修复早退。随后 fixture 改为与真实 Host 一样 await init 消费后再断开 IPC，并打开专门 fixture 的诊断；聚焦作业验证通过。此前早退的具体机制没有足够日志，不能将其归为生产 ConPTY 故障。

最后一轮安全实现验证为 [38139799801](https://github.com/hogancv/coordinate-agents/actions/runs/38139799801)，提交 `c12933c`，overall 为 failure：Windows 22/24 各 5/6；Windows 20 为 4/6（raw 清理和专用 fixture），Ubuntu/macOS 各 6/6；原有 Session/前端回归每个平台 14/14。`Existing platform policy and Session regressions` 使用 `always()` 独立执行，确保 raw probe 失败不会阻止既有行为回归。Windows raw 的资源释放断言依然保留，预期会阻止 native 完整验收变绿。

独立 tarball 在 macOS Node 22/24 下还以 `COORDINATE_AGENTS_PTY_MODE=native` 强制模式完成了两组 7/7 安装验收，包括 Web 进程停止后新 Web 进程重连原 Session。它们不是 fallback 验收。Windows 上的独立 tarball native 安装未单独执行，不能外推为已验证。
